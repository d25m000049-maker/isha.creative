      The problem and the brief

      Checks run late and by hand, after the design is called done.

      The problem

      Accessibility and usability checks often run late and by hand, after a design is considered done, when fixes cost more. AI-assisted design tools now produce screens faster than occasional manual checks can keep up with, so testing needs to run continuously instead of on a schedule.

      The brief

      Design and prototype an AI testing agent for designers, starting with WCAG colour contrast and widening to other checks later. It tests a whole feature (a connected set of frames), re-runs as the file changes, and sends each issue to the team that owns it, with a record of decisions and versions.

      QA here means one feature at a time. Usability testing with real people stays a separate, product-wide activity.

      Why accessibility first

      Colour contrast is the most rule-based check in the process. WCAG sets the thresholds (4.5:1 for normal text, 3:1 for large text and interface components) and the ratio is calculated from two colours, so little judgment is needed. That makes it the safest first check to automate, and a clean test of agentic testing before moving to checks that need judgment.

      Four text colours on white, with ratios calculated by the WCAG formula. Not all of WCAG is this clear: contrast has edge cases such as text over images, and alt text quality, focus order and reading order need judgment.

      P4

      How might we check a design against one current brief?

      Prototype: Setup holds one brief per file, with KPIs and stakeholders. Tasks carry a success condition and a start frame.
      P2, P3

      How might we automate repeatable checks while keeping judgment with people?

      Prototype: Design System Consistency and Accessibility run as Instant, rule-based checks. The designer makes every decision.
      P7

      Prototype: Every result shows its source. Each issue has a Details view, a recommendation and a usefulness rating.
      P6

      How might we hand each issue to the team that owns it?

      Prototype: Issues route to Accessibility, Design system, Content, PM or Product design. The Team view has a Notify team action.
      P5, P7

      How might we confirm AI findings with real people, and keep the record?

      Prototype: Test with people unlocks at a score of 80. The Backlog keeps versions, issues and decisions.

      Design principles built into the prototype

      One feature, one test, one score

      Test Mode checks one finished section at a time. Smaller runs gave results I could actually read and act on.

      The designer decides

      Each issue ends in a decision: Accept recommendation, Resolved, Defer, Won't fix or Dismiss. The owning team can be changed.

      Show the source of every result

      Instant, AI-powered, Simulated or Human, so people know how much to trust each finding.

      Test against the written brief

      People write the brief, KPIs and tasks. The agent tests the design against them and does not interpret a raw PRD.

      AI first, then people confirm

      A run must score 80 before testers are invited. Findings are then classed as AI-predicted or Human-validated.

      Detail on demand

      One main action per screen, in a sticky footer. Evidence sits behind a popover so the panel stays short.

      Information architecture

      How Test Mode is organised

      Test Mode is a mode of the editor, next to Design and Dev Mode. It never opens a separate app. Every screen sits in the right panel, a modal or a popover over the canvas.

      Purpose

      Test one finished feature, a section of frames, before real users see it. Find problems early, explain them in plain words and route each one to the team that owns it.

      Who uses it

      • Designer: sets up, runs, reviews and decides.
      • Owning teams (Accessibility, Design system, Content, PM, Product design): receive issues.
      • Testers: real people invited to confirm findings.

      Structural principles

      • One feature, one test, one score at a time.
      • One main action per screen, in a sticky footer.
      • Detail on demand: modals and popovers, not long panels.
      • Every result is labelled by its source.

      Three ways in

      • Toolbar mode switch: a flask icon before Dev Mode.
      • Agents in the rail: Test Mode is the editor's testing agent.
      • A "Test this section" card at the bottom of the Design panel.

      First time in a file, Test Mode opens on Setup. After that it opens on the last results.

      Site map

      Three tabs in the right panel hold everything: Run, Results and Backlog. Select a part to see what it contains.

      Setup runs once per file. "Test with people" opens from Results but shows under the Run tab. Global in Test Mode: token balance bar, Setup link, zoom, canvas banner and the prototype guide.

      The 13 screens, in order

      Select a screen to see its job and its one primary action.

      Fix loop

      Results (07) to Issue detail (08), record a decision, re-run, get a new version and score, back to Results. The Results tab shows "N changes since version X" until you re-run.

      Gate to people

      "Test with people" stays locked until a run scores 80 or more. The locked card shows the current score and progress toward 80.

      Shortcuts

      Pins on the canvas, layer badges, Teams rows and Backlog rows all open the same issue popover (08). Setup can be reopened any time from the Setup link.

      Issues and scoring

      An issue is the core unit. Every surface (list, pin, layer badge, team group, backlog row) points to the same record.

      What an issue holds

      Score calculator

      Starts at 100. Each open issue takes off Critical −8, Major −6, Minor −3. Deferred and Won't fix still count until closed, and the score only changes when you re-run.

      Verdict bands: Needs work below 70, Almost ready 70 to 79, Ready for people 80 and above.

      Issue lifecycle

        Decisions: Fixed and Resolved close the issue on re-run. Deferred and Won't fix keep it open. Also Accept recommendation, Save for later, Dismiss.

        Classification after people test

        • Automated: measured by rules.
        • AI-predicted: predicted, needs people.
        • Human-validated: confirmed by 2 or more testers.
        • Human-reported: found by people, not yet validated.

        Routing teams

        Accessibility, Design system, Content, PM, Product design. The owner can be changed in Fix and decide.

        Solution

        Which feature answers which pain point

        Select a pin to highlight the features that address it. Screen numbers match the 13 screens above.

        Closing the gap between AI results and real people

        • Every result carries its source: Instant (rules), AI-powered, Simulated or Human.
        • AI personas are labelled Simulated. They explore the feature first, and real testers confirm.
        • "Test with people" stays locked until a run scores 80 or more, so testers see a feature that already passes the basics.
        • Human sessions take their questions from the AI findings. After testing, each finding is classed as Automated, AI-predicted, Human-validated (confirmed by 2 or more testers) or Human-reported.
